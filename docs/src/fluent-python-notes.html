Rule: Python calls special methods, you don't. Write len(x), never x.__len__().

Why len() is fast for built-in types

  1. Python itself is written in C. The standard Python you run is called CPython. Every Python object, such as a list, is a block of memory laid out as a C struct: a fixed record with named fields.
  2. Lists, strings and other collections whose size can change all start with the same struct, PyVarObject. One of its fields, ob_size, holds the current number of items. The list updates it on every append or pop, so len(my_list) just reads that field.
  3. Your own class takes the slow route. For len(deck), Python has to find __len__ on the class, set up a Python function call, and run your code, which here calls len() on the inner list. Same answer, several extra steps.
# a list in memory (simplified)
list object
├── ob_refcnt
├── ob_type   = list
├── ob_size  = 1000 ← len() reads
└── ob_item  → [items...]
# 5 million calls each (measured)
len(list)    0.09s
len(MyList)  0.22s

This is why len is a function, not a method: one syntax for everything, with a fast path for built-ins.

__repr__ vs __str__

__repr__ is for developers: it should show exactly what the object is, ideally looking like the code that recreates it. __str__ is for end users: it just has to be readable. print() calls str(), which uses __str__; if a class has no __str__, it uses __repr__ instead. So if you write only one, write __repr__.

Truthiness: bool(x)

bool(), if x: and while x: check, in order:

  1. __bool__, if defined: use its result (it must return an actual bool).
  2. Otherwise __len__: falsy if it returns 0.
  3. Otherwise: always truthy.

So a collection with only __len__ is falsy when empty, like [] and "".

# Vector: falsy only for Vector(0, 0)
def __bool__(self):
    return bool(abs(self))
# faster: skips the square root
def __bool__(self):
    return bool(self.x or self.y)
# `or` returns an operand (e.g. 3), not
# a bool: hence the bool(...) wrapper.
# bool(3) runs int's __bool__, not
# Vector's: no recursion.

The Collection API

Collection combines Iterable (__iter__), Sized (__len__) and Container (__contains__) by multiple inheritance: class Collection(Sized, Iterable, Container). Together these define what a collection is: something you can loop over, measure and search. The three main kinds, Sequence, Mapping and Set, are each a Collection with extra methods of their own. The ABCs (abstract base classes, in collections.abc) mark the core methods as required and provide the rest for free, built from those.

Rules of thumb
  1. Always write __repr__; add __str__ only if users need a different text.
  2. In operators and __eq__, return NotImplemented for types you don't handle; never crash.

  4. Never call them directly: write len(x), not x.__len__(). Exception: super().__init__().

Container vs Flat · Mutable vs Immutable

Container sequences can hold items of different types. Internally they store references: pointers to separate Python objects living elsewhere in memory.

Flat sequences store raw values directly, packed side by side in one block of memory: str holds characters, bytes holds integers 0-255, array('d') holds floats. One simple type only, but compact: 1M floats take 32 MB in a list vs 8 MB in an array.

# container: [1.5, 2.5, 3.5]
[ ● | ● | ● ]       ← 3 pointers
  ▼   ▼   ▼

# flat: array('d', [1.5, 2.5, 3.5])
[ 1.5 | 2.5 | 3.5 ] ← raw 8-byte values

The MutableSequence ABC inherits every method of the read-only Sequence ABC, plus methods that change things in place. Italic = must implement; the rest come free.

Sequence__getitem__ __len__ __contains__ __iter__ __reversed__ index count
MutableSequence+ __setitem__ __delitem__ insert append extend pop remove reverse __iadd__

An ABC is any abstract base class. Sequence is one of the ready-made ABCs in the collections.abc module.

Why does list count as a MutableSequence without inheriting from it? Built-ins like list and tuple are written in C and are older than the ABCs, and they already implement every method themselves. Instead they are registered: list with MutableSequence, tuple with Sequence. That makes isinstance() and issubclass() return True without inheriting anything (a virtual subclass).

issubclass(list, abc.MutableSequence)  # True
list.__mro__   # (list, object)

Comprehensions, generator expressions and the walrus

Generator expressions are written in parentheses and save memory: items are produced one at a time, on demand. As a sole argument, they need no extra parentheses.

# listcomp: builds the whole list
[ord(s) for s in symbols if ord(s) > 127]
[(c, s) for c in colors for s in sizes]
# genexp: yields items one by one
sum(len(w) for w in words)
tuple(ord(s) for s in symbols)

The walrus operator := assigns a value and returns it in the same expression. Use it to avoid computing something twice. Wrap it in parentheses.

while (chunk := f.read(4096)):
    process(chunk)
[p for l in lines
   if (p := parse(l)) is not None]

Tuples

Tuples are either records, where position gives meaning (unpack them into names), or immutable lists, where the length and contents can never be swapped out.

A tuple stores references, like any container sequence, so it's only truly fixed if everything inside it is immutable too. A tuple holding a mutable object can't be hashed, so it can't be a dict key or a set item.

# record: unpack by position
city, year, pop = ("Tokyo", 2003, 32_450)
for country, _ in traveler_ids: ...
# relative immutability
b = (10, "alpha", [1, 2])
b[-1].append(99)   # OK: list inside changes
b[-1] = [5]        # TypeError
hash(b)            # TypeError

Pattern matching sequences: match/case

match/case checks the shape of a sequence and pulls it apart in one step. The pattern looks like the data it matches. Cases are tried top to bottom; the first match wins.

FeatureExample
Literals + length['go', direction]
Rest, as a list['drop', *items]
Nested structure[name, _, _, (lat, lon)]
Type check['move', int(x), int(y)]
Ignore / name_ · (lat, lon) as coord
Alternatives['3' | '4', *rest]

match command:
    case ['go', direction]:
        return f"go {direction}"
    case ['drop', *items]:
        return f"dropped {len(items)}"
    case ['move', int(x), int(y)]:
        return f"moved to ({x}, {y})"
    case _:           # catch-all
        return "unknown command"

str, bytes and iterators never match sequence patterns. Use match tuple(s): or match list(it):.

Slicing

1. Slice objects. a:b:c is shorthand for slice(a, b, c): Python builds the object and passes it to __getitem__. So you can name your slices, which keeps fixed-width data readable and easy to change.

2. Several dimensions. Commas in [] pass a tuple of keys, one per dimension. Built-in sequences are 1D; NumPy uses it.

3. Ellipsis ... fills in : for every dimension not mentioned.

SKU   = slice(0, 6)
PRICE = slice(40, 52)
print(line[SKU], line[PRICE])
# "abc"[1:3] == "abc"[slice(1, 3)]
a[1, 2]        # row 1, column 2

b[0, ...]      # 3D: same as b[0, :, :]

4. Assigning to slices replaces, deletes or inserts a chunk of a mutable sequence in place.

  1. The right side must be iterable, even for one item: l[2:5] = [100], not = 100.

  3. A stepped slice needs an exact length match, or ValueError.

Threads, the GIL and asyncio Extra · not in the chapter

Concurrency: several jobs are in progress at once, and the CPU switches between them.

Parallelism: several jobs run at the same instant, on different CPU cores.

Python has real OS threads, but the GIL (Global Interpreter Lock) lets only one thread run Python code at a time. So for Python code, threads give concurrency, not parallelism.

CPU-bound (calculating): each thread needs the GIL () the whole time, so they take turns: the staircase. The GIL is the bottleneck, not the CPU (other cores sit idle), so use multiprocessing: one GIL per process.

I/O-bound (waiting on network, disk, q.get()): a thread runs briefly (), then releases the GIL while it waits (····), so the waits overlap: threads suit I/O-bound work.

Pattern matching with mappings

match record:
    case {'type': 'book', 'api': 2,
          'authors': [*names]}:
        return names
    case {'type': 'book', 'api': 1,
          'author': name}:
        return [name]
    case {'type': 'book'}:       # known type,
        raise ValueError(...)    # bad record
    case {'type': 'movie', 'director': name}:
        return [name]
    case _:                      # catch-all
        raise ValueError(...)
case {'category': 'ice cream', **details}:
    # details = all the OTHER keys

A mapping pattern means "has these keys, with values matching these patterns". Values can be any pattern, including sequence patterns.

Partial matches succeed: extra keys are ignored and order doesn't matter (sequence patterns need an exact length). Ideal for JSON-like records.

**rest captures the extra keys; it must come last. **_ is not allowed.

Lookups use d.get(key, sentinel), so a defaultdict never invents keys during a match.

For records: include a type field and a schema version field, and add a case for invalid records of a known type plus a catch-all.

What is hashable

Hashable means: the hash never changes (__hash__), the object supports == (__eq__), and equal objects have equal hashes. A dict finds keys by hash first, so equal keys with different hashes would never be found.

Your classes hash by id() by default. Defining __eq__ sets __hash__ to None; to fix it, hash the same attributes as __eq__, and keep them unchanging.

str/bytes hashes are salted per process: never store them.

Check isinstance(x, abc.Mapping), not dict, to also accept MappingProxyType, ChainMap and UserDict.

dict is a concrete C class. Like list, it is registered as a virtual subclass: MutableMapping.register(dict).

dict.__mro__     # (dict, object)

UserDict is the base for your own mappings: plain Python, a real MutableMapping subclass, storing a dict in self.data.

Why not subclass dict? Its C methods (constructor, update, get, in) skip your overrides. UserDict's methods go through self[k], so one override covers every path.

# override __setitem__ to store str(k)
# x = X({1: 'a'}); x[2] = 'b'
# x.update({3: 'c'}); then the stored keys:
D(dict):     {1: 'a', '2': 'b', 3: 'c'}  ✗
U(UserDict): {'1': 'a', '2': 'b', '3': 'c'} ✓

Write to self.data, not self, or it recurses.

Missing keys: __missing__ and defaultdict

When d[k] misses, dict.__getitem__ calls __missing__(k) if the subclass defines it, instead of raising KeyError.

defaultdict is exactly this: a dict subclass whose __missing__ calls default_factory(), stores the result under k and returns it.

To build a custom dict, subclass UserDict. When you add __missing__ to it, override __contains__ too, so in and get agree with d[k].

Immutable mappings: MappingProxyType

types.MappingProxyType(d) wraps a dict in a read-only, live proxy:

  • Read-only: nothing can be added, changed or deleted through the proxy.
  • Live: it's a view, not a copy, so changes to d itself show up.

Use when others should read a dict but not change it: keep the real dict private and expose the proxy. It is a Mapping but not a MutableMapping.

d = {1: 'A'}
d_proxy = MappingProxyType(d)
d_proxy[1]        # 'A'
d_proxy[2] = 'x'  # TypeError
d[2] = 'B'        # change the original...
d_proxy           # ...{1: 'A', 2: 'B'}
class Board:
    def __init__(self):
        self._pins = {13: 'LED'}  # private
        self.pins = MappingProxyType(
            self._pins)          # public

Practical consequences of how dict works

A dict is a hash table: hash(key) picks a slot, and == confirms the key: no scanning. Timings are for 1M lookups.

Set theory

A set is a collection of unique objects: set is mutable, frozenset immutable. Basic use: removing duplicates (dict.fromkeys also keeps first-seen order).

Elements must be hashable. A set isn't, so sets can't nest; a frozenset is, so it can go in a set or be a dict key.

Operators replace loops: | union, & intersection, - difference, ^ symmetric difference. Operators need sets on both sides; methods (.intersection(), ...) take any iterable.

Literals are faster: {1, 2, 3} compiles to one BUILD_SET instruction; set([1, 2, 3]) looks up set, builds a list, then calls it (1M runs: 0.021s vs 0.054s).

l = ['spam', 'eggs', 'spam']
set(l)                  # {'eggs', 'spam'}
list(dict.fromkeys(l))  # ['spam', 'eggs']
{{1, 2}}               # TypeError
{frozenset({1, 2}), 3} # OK
a = {1, 2, 3}
b = {2, 3, 4}
a | b  # {1, 2, 3, 4} union: in either
a & b  # {2, 3}  intersection: in both
a - b  # {1}     difference: in a, not b
a ^ b  # {1, 4}  symmetric: in exactly one
a & [3, 9]             # TypeError
a.intersection([3, 9])  # {3}: any iterable

Like dicts (both are hash tables): elements must be hashable, x in s is fast at any size, and memory use is high.

Unlike dicts: no order. Elements are placed by hash, and adding more can rearrange them. For unique and ordered, use dict.fromkeys.

6Object References, Mutability, and Recycling

Book pages 201-230 · code in fluent-python/ch06/

A name is not the object: a variable is a label that refers to an object.

Variables are labels, not boxes

b = a copies nothing: it sticks a second label on the object a already refers to. Two names for one object are aliases.

Mutating (append, a[0] = ..., list +=) changes the object, so every label sees it. = never changes an object: it only moves a label. So aliasing surprises only involve mutable objects.

a = [1, 2, 3]
b = a           # two labels, ONE list
a.append(4)     # mutate
b               # [1, 2, 3, 4]
a = [9]         # rebind a only
b               # [1, 2, 3, 4]

Assignment happens right to left

The right side runs first and creates or finds the object; only then is the name on the left bound to it. If the right side fails, the name is never created.

y = Gizmo() * 10
# a Gizmo IS created, then * raises TypeError
'y' in globals()   # False: y never bound

Use is only for singletons: None and sentinels (is not to negate). Everything else: ==; is may happen to work on small ints, hiding the bug.

int('1000') is int('1000')  # False
int('1000') == int('1000')  # True

Tuples hold fixed references

A tuple stores references. Immutable means those references never change, but a mutable object it refers to can. So the identity of its items is fixed, while its value may change. This is why a tuple holding a list is unhashable, and behind the Ch 2 += puzzler.

t1 = (1, 2, [30, 40])
t2 = (1, 2, [30, 40])
t1 == t2             # True
t1[-1].append(99)    # same list, new value
t1                   # (1, 2, [30, 40, 99])
t1 == t2             # False

Shallow vs deep copies

Shallow (list(a), a[:], a.copy(), copy.copy(a), the default): a new outer container holding the same items. Fine if the items are immutable; a shared mutable item changes in both.

Deep (copy.deepcopy(a)): copies everything inside, at any depth, so nothing is shared. Handles cycles; customize with __deepcopy__.

a = [1, [2, 3]]
s = list(a)           # shallow
d = copy.deepcopy(a)  # deep
a[1].append(4)        # change the inner list
s                     # [1, [2, 3, 4]] shared
d                     # [1, [2, 3]]    own

Mutable defaults and defensive copying

Never use a mutable default. A default value is made only once, not on every call. Every call that skips the argument gets the same list, so what one call adds is still there in the next.

Fix: default to None, and create a new object inside the function.

def add(x, target=[]):      # BAD
    target.append(x)
    return target
add(1)              # [1]
add(2)              # [1, 2]  same list!
# GOOD: target=None, then
#   if target is None: target = []

Defensive copying. If you keep a mutable argument, store your own copy. Otherwise your object and the caller share one list, and changing yours changes theirs.

class Bus:
    def __init__(self, passengers):
        self.passengers = passengers  # BAD
team = ['Sue', 'Tina']
Bus(team).passengers.remove('Tina')
team                # ['Sue']  changed too!
# GOOD: self.passengers = list(passengers)

del and garbage collection

del x deletes the name, not the object. The object lives while any name still refers to it; rebinding the last name frees it too.

Reference counting (CPython): each object counts the references to it, and is freed the moment the count hits 0. Objects that refer to each other (a cycle) never reach 0, so a separate cycle collector (gc) frees them later.

Avoid __del__: it doesn't delete anything, it's only called just before destruction, and when isn't guaranteed. Clean up with with or close().

a = [1, 2]
b = a
del a        # removes the name a only
b            # [1, 2]: still alive
b = [3]      # last name gone → freed
x.other = y  # x → y
y.other = x  # y → x: a cycle
del x, y     # counts stay at 1...
gc.collect() # ...gc frees them

7Functions as First-Class Objects

Book pages 231-252 · code in fluent-python/ch07/

Functions are objects

In Python, every function is a first-class object: it can be created at runtime, assigned to a variable or stored in a data structure, passed as an argument, and returned from a function.

A function is an instance of function, with attributes like __name__ and __doc__. def just binds a name to a new function object.

f is the function; f() calls it. Pass f without parentheses to let something else call it later.

# a function is an object
def factorial(n):
    """returns n!"""
    if n < 2:
        return 1
    return n * factorial(n - 1)

type(factorial)     # <class 'function'>
factorial.__doc__   # 'returns n!'
# 1. assign it to another name
fact = factorial    # same object
fact(5)             # 120
# 2. store it in a data structure
ops = {'mul': lambda a, b: a * b}
ops['mul'](3, 4)    # 12
# 3. pass it as an argument
list(map(factorial, range(6)))
# [1, 1, 2, 6, 24, 120]
# 4. return it from a function
def make_adder(n):
    def add(x):
        return x + n
    return add
make_adder(5)(10)   # 15

Higher-order functions

A higher-order function takes a function as an argument or returns one as output, like sorted, max and min with key=. Any one-argument function works as a key.

sorted(fruits, key=len)
# ['fig', 'apple', 'cherry', ...]

Lambda: lambda params: expr makes a small unnamed function whose body is one expression (no statements). Use it as a short argument to a higher-order function; otherwise use def.

sorted(fruits, key=lambda w: w[::-1])
# ['banana', 'apple', 'fig', ...]

The classic trio. map(f, it) applies f to every item; filter(f, it) keeps items where f(item) is truthy; reduce(f, it) (in functools) combines items two at a time into one value.

list(map(str, [1, 2]))       # ['1', '2']
list(filter(None, [0, 1, 2])) # [1, 2]
reduce(add, [1, 2, 3, 4])     # 10
# add(1, 2)→3, add(3, 3)→6, add(6, 4)→10

map and filter return lazy iterators: items are computed one at a time, only when asked for (next(), for, list()), so they use almost no memory. They are one-pass: once used up, they're empty.

m = map(square, [1, 2, 3])  # no work yet
next(m)                     # computes 1 now
list(m)                     # [4, 9]: the rest
list(m)                     # []: used up

Callables

A callable is anything you can call with (): functions, built-in functions and methods, methods, classes (calling one creates an instance), and instances whose class defines __call__. Check with callable(obj).

callable(len)     # True: a function
callable(str)     # True: a class
callable('Ni!')   # False

Make your own: define __call__, and obj(...) runs obj.__call__(...).

Why not a function? A function forgets its local variables when it returns; an object keeps state in its attributes between calls, and you can inspect it.

class Adder:
    def __init__(self):
        self.total = 0
    def __call__(self, x):
        self.total += x
        return self.total

add = Adder()
add(5)      # 5
add(10)     # 15: remembered the 5
add.total   # 15

*args vs bare *: both make every parameter after them keyword-only. *args collects extra positional arguments into a tuple; a bare * rejects them with a TypeError.

def f(a, *args, b): ...
f(1, 2, 3, b=4)   # args=(2, 3)
def g(a, *, b): ...
g(1, 2, b=4)      # TypeError

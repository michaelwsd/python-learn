Rule: Python calls special methods, you don't. Write len(x), never x.__len__().

Why len() is fast for built-in types

  1. Python itself is written in C. The standard Python you run is called CPython. Every Python object, such as a list, is a block of memory laid out as a C struct: a fixed record with named fields.
  2. Lists, strings and other collections whose size can change all start with the same struct, PyVarObject. One of its fields, ob_size, holds the current number of items. The list updates it on every append or pop, so len(my_list) just reads that field.
  3. Your own class takes the slow route. For len(deck), Python has to find __len__ on the class, set up a Python function call, and run your code, which here calls len() on the inner list. Same answer, several extra steps.
# a list in memory (simplified)
list object
├── ob_refcnt
├── ob_type   = list
├── ob_size  = 1000 ← len() reads
└── ob_item  → [items...]

# 5 million calls each (measured)
len(list)    0.09s
len(MyList)  0.22s

This is why len is a function, not a method: one syntax for everything, with a fast path for built-ins.

__repr__ vs __str__

__repr__ is for developers: it should show exactly what the object is, ideally looking like the code that recreates it. __str__ is for end users: it just has to be readable. print() calls str(), which uses __str__; if a class has no __str__, it uses __repr__ instead. So if you write only one, write __repr__.

That's why the chapter's Vector uses !r: f"Vector({self.x!r}, {self.y!r})".

Truthiness: bool(x)

bool(), if x: and while x: check, in order:

  1. __bool__, if defined: use its result (it must return an actual bool).
  2. Otherwise __len__: falsy if it returns 0.
  3. Otherwise: always truthy.

So a collection with only __len__ is falsy when empty, like [] and "".

# Vector: falsy only for Vector(0, 0)
def __bool__(self):
    return bool(abs(self))

# faster: skips the square root
def __bool__(self):
    return bool(self.x or self.y)
# `or` returns an operand (e.g. 3), not
# a bool: hence the bool(...) wrapper.
# bool(3) runs int's __bool__, not
# Vector's: no recursion.

The Collection API

Collection combines Iterable (__iter__), Sized (__len__) and Container (__contains__) by multiple inheritance: class Collection(Sized, Iterable, Container). Together these define what a collection is: something you can loop over, measure and search. The three main kinds, Sequence, Mapping and Set, are each a Collection with extra methods of their own. The ABCs (abstract base classes, in collections.abc) mark the core methods as required and provide the rest for free, built from those.

from collections.abc import Sequence

class Playlist(Sequence):
    def __init__(self, songs):
        self._songs = list(songs)
    def __getitem__(self, i):     # required
        return self._songs[i]
    def __len__(self):            # required
        return len(self._songs)

p = Playlist(["a", "b", "a"])

p.index("b")       # 1      free

Rules of thumb
  1. Always write __repr__; add __str__ only if users need a different text.
  2. In operators and __eq__, return NotImplemented for types you don't handle; never crash.
  3. Define __eq__ → decide on __hash__: hash the same fields, or stay unhashable if mutable.
  4. Never call them directly: write len(x), not x.__len__(). Exception: super().__init__().

Container vs Flat · Mutable vs Immutable

Container sequences can hold items of different types. Internally they store references: pointers to separate Python objects living elsewhere in memory.

Flat sequences store raw values directly, packed side by side in one block of memory: str holds characters, bytes holds integers 0-255, array('d') holds floats. One simple type only, but compact: 1M floats take 32 MB in a list vs 8 MB in an array.

# container: [1.5, 2.5, 3.5]
[ ● | ● | ● ]       ← 3 pointers
  ▼   ▼   ▼
 1.5 2.5 3.5        ← 3 full float objects

# flat: array('d', [1.5, 2.5, 3.5])
[ 1.5 | 2.5 | 3.5 ] ← raw 8-byte values

The MutableSequence ABC inherits every method of the read-only Sequence ABC, plus methods that change things in place. Italic = must implement; the rest come free.

Sequence__getitem__ __len__ __contains__ __iter__ __reversed__ index count
MutableSequence+ __setitem__ __delitem__ insert append extend pop remove reverse __iadd__

An ABC is any abstract base class. Sequence is one of the ready-made ABCs in the collections.abc module.

Why does list count as a MutableSequence without inheriting from it? Built-ins like list and tuple are written in C and are older than the ABCs, and they already implement every method themselves. Instead they are registered: list with MutableSequence, tuple with Sequence. That makes isinstance() and issubclass() return True without inheriting anything (a virtual subclass).

issubclass(list, abc.MutableSequence)  # True
list.__mro__   # (list, object)

Comprehensions, generator expressions and the walrus

# listcomp: builds the whole list
[ord(s) for s in symbols if ord(s) > 127]
[(c, s) for c in colors for s in sizes]

# genexp: (...) yields items one by one,
# no list in memory
sum(len(w) for w in words)
tuple(ord(s) for s in symbols)

Generator expressions are written in parentheses and save memory: items are produced one at a time, on demand. As a sole argument, they need no extra parentheses.

The walrus operator := assigns a value and returns it in the same expression. Use it to avoid computing something twice. Wrap it in parentheses.

while (chunk := f.read(4096)):
    process(chunk)
[p for l in lines
   if (p := parse(l)) is not None]

Tuples

Tuples are either records, where position gives meaning (unpack them into names), or immutable lists, where the length and contents can never be swapped out.

A tuple stores references, like any container sequence, so it's only truly fixed if everything inside it is immutable too. A tuple holding a mutable object can't be hashed, so it can't be a dict key or a set item.

# record: unpack by position
city, year, pop = ("Tokyo", 2003, 32_450)
for country, _ in traveler_ids: ...

# relative immutability
b = (10, "alpha", [1, 2])
b[-1].append(99)   # OK: list inside changes
b[-1] = [5]        # TypeError
hash(b)            # TypeError

Pattern matching sequences: match/case

match/case checks the shape of a sequence and pulls it apart in one step. The pattern looks like the data it matches. Cases are tried top to bottom; the first match wins.

FeatureExample
Literals + length['go', direction]
Rest, as a list['drop', *items]
Nested structure[name, _, _, (lat, lon)]
Type check['move', int(x), int(y)]
Ignore / name_ · (lat, lon) as coord
Alternatives['3' | '4', *rest]
Guard[...] if lon <= 0
 
match command:
    case ['go', direction]:
        return f"go {direction}"
    case ['drop', *items]:
        return f"dropped {len(items)}"
    case ['move', int(x), int(y)]:
        return f"moved to ({x}, {y})"
    case _:           # catch-all
        return "unknown command"

str, bytes and iterators never match sequence patterns. Use match tuple(s): or match list(it):.

Slicing

1. Slice objects. a:b:c is shorthand for slice(a, b, c): Python builds the object and passes it to __getitem__. So you can name your slices, which keeps fixed-width data readable and easy to change.

2. Several dimensions. Commas in [] pass a tuple of keys, one per dimension. Built-in sequences are 1D; NumPy uses it.

3. Ellipsis ... fills in : for every dimension not mentioned.

SKU   = slice(0, 6)
PRICE = slice(40, 52)
print(line[SKU], line[PRICE])
# "abc"[1:3] == "abc"[slice(1, 3)]

a[1, 2]        # row 1, column 2
a[:, 0]        # every row, column 0
a[0:2, 1:3]    # a 2x2 block
b[0, ...]      # 3D: same as b[0, :, :]

4. Assigning to slices replaces, deletes or inserts a chunk of a mutable sequence in place.

  1. The right side must be iterable, even for one item: l[2:5] = [100], not = 100.
  2. A plain slice can change the length: replace 3 items with 2 and the list shrinks.
  3. A stepped slice needs an exact length match, or ValueError.

Threads, the GIL and asyncio

Concurrency: several jobs are in progress at once, and the CPU switches between them.

Parallelism: several jobs run at the same instant, on different CPU cores.

Python has real OS threads, but the GIL (Global Interpreter Lock) lets only one thread run Python code at a time. So for Python code, threads give concurrency, not parallelism.

CPU-bound (calculating): each thread needs the GIL the whole time, so they take turns: the staircase. The GIL is the bottleneck, not the CPU (other cores sit idle), so use multiprocessing: one GIL per process.

I/O-bound (waiting on network, disk, q.get()): a thread runs briefly (█), then releases the GIL while it waits (····), so the waits overlap: threads suit I/O-bound work.

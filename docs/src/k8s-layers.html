A2 · Where things run

Image and container

A Dockerfile builds an image: your program plus everything it needs. Running the image creates a container, an isolated copy that behaves the same on any machine.

Dockerfile

FROM python:3.14-slim
COPY --from=uv /uv /bin/uv
RUN uv sync --no-dev
COPY src ./src
ENTRYPOINT ["pinger"]
build

Image pinger:0.1.0

src/ changes often
dependencies
uv binary
python:3.14-slim base
run ×3

Containers

pinger own fs
pinger own net
pinger own pids
Registry Docker Hub, ghcr.io. You push images to it, and every machine that needs one pulls it from there.
  • Image: a read-only package of the OS files, Python, dependencies and your code. Each Dockerfile line adds a cached layer, which is why src/ is copied last.
  • Container: a running instance of one image. It gets a thin writable layer on top, which is thrown away when the container is removed.
  • One image can run as many containers. Each container runs exactly one image.
Image : containeris the same relationship asclass : instanceOne definition, many running copies.
See it on minikube 
minikube image build -t pinger:0.1.0 .   # build inside the cluster
minikube image ls | grep pinger           # the image is now available to run
Still unsolved

A container on its own doesn't restart when it crashes, doesn't scale, and knows nothing about other machines. A3 →

A3 · Where things run

Pod

The smallest thing Kubernetes runs. It's a wrapper that gives one container (sometimes a few) its own IP and the settings Kubernetes needs to manage it.

Podweb-7d4b9-x2kqIP 10.244.0.7
appnginx · :80
localhost
log-shippersidecar
shared volume /var/log/nginx

Containers in a Pod share one IP and its volumes, always run on the same node, and are deleted together.

Pods are replaced, never repaired
web-7d4b9-x2kq10.244.0.7
Running
web-7d4b9-x2kq10.244.0.7
Deleted
web-7d4b9-p9zt10.244.0.12
Running

The replacement has a new name and a new IP. A single crashed container is different: kubelet restarts it inside the same Pod, which shows in the RESTARTS column.

  • Most Pods hold one container. Add a second one (a sidecar) only when it must share files or localhost with the first, such as a log shipper or a proxy.
  • Don't put a web app and its database in one Pod. They need to scale separately.
See it on minikube 
kubectl get pods -o wide        # shows each Pod's IP, node and restarts
kubectl describe pod <name>     # containers, events, restarts
kubectl logs <name> -c app      # -c picks a container in a multi-container Pod

A4 · Where things run

Node

A machine, virtual or physical, that runs Pods. Three agents on every node do the actual work.

API server: "run web-x2kq on minikube"→ kubelet→ containerd pulls + starts→ container running
Node: minikube4 CPU · 8 GiB · Linux VM

kubelet

Manages the node. Runs the Pods assigned here, restarts crashed containers, and reports status back.

containerd

The container runtime. Pulls images and starts and stops containers.

kube-proxy

Writes network rules so traffic sent to a Service reaches a Pod.

web-x2kq web-p9zt pinger-ok-4mz
  • The kubelet only carries out decisions. Choosing which node a Pod goes to is the scheduler's job (C1).
  • If a node dies, its Pods aren't moved. They're replaced on healthy nodes.
See it on minikube 
kubectl get nodes -o wide       # one node, called minikube
kubectl describe node minikube  # capacity, conditions, Pods on it

Cluster and Namespace

A cluster is a control plane plus all its nodes, working as one big computer. Namespaces divide the cluster into logical folders.

Namespaces are logical, not physical. Pods from one namespace can be spread across any node. A namespace scopes names, permissions and quotas.

Part B

What you declare

API objects are records you write in YAML and send with kubectl apply. Each one is stored in etcd. Each says what you want (its spec) and records what's actually happening (its status).

These aren't layers. They don't contain Pods the way a node does. They sit beside the Pods and manage them: they point at Pods with a label selector, then create, delete or route traffic to them. Each one is a feature.

Strictly, Pods and Nodes are API objects too. The difference is that a Pod record describes something actually running, while a Deployment or Service record describes how to manage Pods.

B1 · What you declare

Labels and selectors

Key-value tags on Pods, plus queries that match them. Every other object in this part uses them to find its Pods.

Selector

How an object points at Pods

Service web

selector:
  app: web
matches

Pods with that label

metadata:
  labels:
    app: web
    env: prod

The object stores a query, not a list of names. A replacement Pod with the right labels is picked up automatically, whatever its name or IP.

See it on minikube 
kubectl get pods --show-labels
kubectl get pods -l app=web               # -l is a label selector
kubectl get pods -l 'app=web,env=prod'    # comma means AND

B2 · What you declare

ReplicaSet and Deployment

A ReplicaSet keeps N matching Pods running. A Deployment manages ReplicaSets so you can roll out new versions and roll them back.

Self-healing: try breaking it
ReplicaSet web-7d4b9selector app=web
desired 3running 3

The ReplicaSet controller compares desired with running and acts on the difference.

Rolling update: nginx:1.27 → nginx:1.28, 4 replicas
Deployment webmaxSurge 25% = +1 · maxUnavailable 25% = −1
ReplicaSet web-5f8cimage nginx:1.27
ReplicaSet web-7d4bimage nginx:1.28
Pods in total 4 / max 5
Pods serving 4 / min 3

    v1 Pod ready v2 Pod ready v2 Pod starting
    • The chain of ownership is Deployment → ReplicaSet → Pods. You create the Deployment, and the objects below it are created for you.
    • The old ReplicaSet is kept at 0 replicas, so rollout undo just scales it back up.
    See it on minikube 
    kubectl create deployment web --image=nginx:1.27 --replicas=4
kubectl scale deployment web --replicas=6
kubectl set image deployment/web nginx=nginx:1.28
kubectl rollout status deployment/web
kubectl get rs                           # old ReplicaSet at 0, new one at 6
kubectl rollout undo deployment/web

    B3 · What you declare

    Service

    A stable name and IP in front of a changing set of Pods. The Pods behind it are chosen by a label selector.

    Client Pod

    curl http://web

    Cluster DNS turns web into the Service IP.

    Service webClusterIP 10.96.142.7:80
    selector app=web
    address never changes
    Service types: each one builds on the one inside it
    LoadBalancera cloud load balancer with a public IP, sending traffic to the NodePort
    NodePorta port (30000-32767) opened on every node
    ClusterIPdefault · only reachable inside the cluster

    The Service object is only a record. kube-proxy on each node (A4) turns it into real network rules. On minikube on a Mac, use kubectl port-forward or minikube service --url.

    See it on minikube 
    kubectl expose deployment web --port 80 --type NodePort
kubectl get svc web
kubectl get endpointslices -l kubernetes.io/service-name=web   # current Pod IPs
kubectl port-forward svc/web 8080:80                           # then open localhost:8080

    Job and CronJob

    A Job runs Pods until the work succeeds. A CronJob creates a new Job on a schedule.

    Retries back off: each wait is longer than the one before. backoffLimit: 2 means 2 retries after the first failure, so 3 attempts in total.

    • The exit code decides success: 0 means Complete, and anything else is retried. That's why pinger returns 1 when a URL is down.
    • Ownership again: CronJob → Job → Pod. Deleting the parent deletes the children.
    See it on minikube 
    kubectl create job pinger-ok --image=pinger:0.1.0 -- pinger https://example.com
kubectl get jobs,pods
kubectl create job manual-run --from=cronjob/pinger   # trigger a CronJob now

    What makes it happen

    The control plane isn't a layer either. It's the machinery that connects the other two parts: it stores the objects from Part B, and its controllers keep changing Part A until reality matches them.

    objects (B) → controllers (C) → running Pods (A)
    C1 Control planeC2 Desired stateC3 End to end
    C1 · What makes it happen

    Control plane

    Four components. One of them stores state, and the other three watch that state and act on it.

    kube-apiserver

    Every read and write goes through it. It validates requests, authenticates callers, and lets other components watch for changes.

    etcd

    A key-value store holding every object. If you lose etcd, the cluster forgets everything, so it's the part you back up.

    kube-scheduler

    Finds Pods with no node yet and picks one for each, based on free CPU and memory and any constraints.

    kube-controller-manager

    Runs one controller per object kind. Each controller is a loop that makes its objects true.

    Every object in Part B has a controller

    C2 · What makes it happen

    Desired state

    You never tell Kubernetes "start a container". You declare what you want, and controllers close the gap.

    spec · you write it (B)

    kind: Deployment
spec:
  replicas: 3
  template:
    image: nginx:1.28
    controller (C)
    closes the gap

    status · what runs (A)

    status:
  replicas: 3
  readyReplicas: 2
  # 1 Pod still starting

    This is reconciliation. It's why a deleted Pod comes back, and why running kubectl apply -f on the same file twice changes nothing the second time.

    C3 · All three parts at once

    One command, end to end

    What happens after kubectl create deployment web --image=nginx --replicas=3. Click a step, or walk through them in order.

    • Every line passes through the API server. No component calls another one directly. Each one watches for the objects it cares about and does its own small job.

1Python General Knowledge

__init__.py

The code that runs when a package is imported. import httpx runs httpx/__init__.py.

__all__

A list of name strings defining the module's public API: what from module import * brings in.

[project.scripts] in pyproject.toml

Defines terminal commands. The format is command = "package:function".

[project.scripts]
pinger = "pinger:main"     # "pinger" in the terminal runs main() from package pinger

Generators (yield)

A function containing yield is a generator. It can pause partway through, hand a value out, and later continue from that exact point.

async / await

Concurrency on one thread. The event loop keeps a list of tasks and runs whichever is ready (not waiting). It can't interrupt a task: the task gives back control voluntarily at each await. Best for I/O waits like network calls.

Decorators

A decorator takes a function and returns a new function (the wrapper) that runs extra code around a call to the original. It works because functions are values: greet is the function itself, greet() calls it. Used for timing, logging, retries and permission checks.

def hello(func):                 # func = the ORIGINAL greet
    def wrapper(*args, **kwargs):
        print("before")
        result = func(*args, **kwargs)  # call original
        print("after")
        return result            # pass its return value back
    return wrapper               # returned, NOT called

@hello                           # same as: greet = hello(greet)
def greet(): print("hi")
greet()                          # before / hi / after
1
@hello runs greet = hello(greet): the original is passed in as func.
2
hello defines wrapper and returns it, so the name greet now points at the wrapper.
3
The wrapper still remembers func after hello has finished. This is a closure.
4
greet() runs the wrapper: prints before, calls the original (hi), prints after.

Why *args, **kwargs? The wrapper replaces the original, so it must accept any arguments and pass them on unchanged: *args packs positional ones into a tuple, **kwargs keyword ones into a dict, and func(*args, **kwargs) unpacks them. Without them, greet("Alice") raises a TypeError.

@hello
def greet(name, loud=False):
    print(name.upper() if loud else name)
greet("Alice", loud=True)
# args=("Alice",)  kwargs={"loud": True}
# before / ALICE / after

2uv Package Manager

uv is one fast tool that replaces pip, venv, pip-tools, pyenv and pipx. You edit dependencies with uv commands; uv keeps three things in step:

pyproject.tomlWhat you wantDependencies and their allowed ranges (httpx>=0.28). Commit it.
uv.lockExactly what you getEvery package pinned to one version, for every platform. Commit it; never edit by hand.
.venv/What's installedThe project's environment, rebuilt from the lockfile. Never commit it.
Daily workflow git pull → uv sync → uv add PKG (when you need one) → uv run pytest → commit both pyproject.toml and uv.lock.

2.2 Key distinctions

uv add --dev vs uv tool install

uv add --dev pytest: part of this project, pinned in its lockfile, so every teammate and CI gets the same version.

uv tool install ruff: a command on your machine, for every project, in its own isolated env.

uv sync vs --locked vs --frozen

uv sync: pyproject.toml wins; updates the lock if needed. For local work.

--locked: lock must already match, else error. For CI and Docker.

--frozen: trust the lock, don't check it at all.

3Docker: Writing a Dockerfile

A Dockerfile is a recipe that builds an image, one instruction at a time. Each instruction runs at build time and saves its result as a cached layer; the stacked layers are the image. Only ENTRYPOINT / CMD describe run time: what a container does when it starts. Example: the pinger CLI from Module 1.

3.1 Annotated example: uv/pinger/Dockerfile

Base and tools
1FROM python:3.14-slimStart from the official image: minimal Debian + Python 3.14 (~120 MB vs ~1 GB full). Must satisfy requires-python.
2COPY --from=ghcr.io/astral-sh/uv:0.13.7 \ /uv /bin/uvCopy just the uv binary out of uv's official image into ours. --from copies from another image; the pinned version keeps builds reproducible.
Setup
3WORKDIR /appmkdir -p /app && cd /app inside the image, for all later steps. Containers also start here.
4ENV UV_COMPILE_BYTECODE=1 \ UV_LINK_MODE=copyPrecompile .py → .pyc once at build, so containers start faster. Copy files instead of linking to uv's cache, which isn't kept in the image.
Dependencies (slow, rarely change → cached)
5COPY pyproject.toml uv.lock README.md ./Copy only the dependency files into ./ = /app/. Last argument is the destination in the image; the rest are sources from the build context.
6RUN uv sync --locked --no-dev \ --no-install-projectInstall dependencies only (httpx...) into /app/.venv. --locked: exactly uv.lock. --no-dev: skip pytest/ruff. --no-install-project: not pinger yet (its code isn't here).
Project (fast, changes often)
7COPY src ./srcNow copy the source code.
8RUN uv sync --locked --no-devInstall pinger itself; creates /app/.venv/bin/pinger from [project.scripts].
Run time
9ENV PATH="/app/.venv/bin:$PATH"Put the venv's bin first in the command search path, so pinger and the venv's python are found. The image version of "activating" a venv.
10ENTRYPOINT ["pinger"]What the container runs. Run-time arguments are appended: -- https://example.com → pinger https://example.com.
Checklist for any Dockerfile Small, pinned base image · pin tool versions · dependency files before source code · install from the lockfile without dev tools · .dockerignore for local junk · exec-form ENTRYPOINT · no secrets in the image · tag every build with a real version.

3.2 Key ideas

Layer caching: copy what rarely changes first

Docker reuses a step's cached layer until its inputs change, then re-runs that step and every step after it. Splitting uv sync in two means a code edit skips the slow dependency install:

you edit src/pinger/__init__.py:
  1-4  FROM, COPY uv, WORKDIR, ENV           CACHED
  5    COPY pyproject.toml uv.lock README.md  CACHED  (unchanged)
  6    RUN uv sync --no-install-project       CACHED  (slow step skipped)
  7    COPY src ./src                         RE-RUN  (input changed)
  8-10 RUN uv sync, ENV, ENTRYPOINT           RE-RUN  (after a change; fast)

With a single COPY . . + RUN uv sync, every code edit would reinstall all dependencies.

Exec form: ["pinger"]

The JSON-list form runs pinger directly as PID 1. The shell form ENTRYPOINT pinger wraps it in /bin/sh -c: stop signals from Kubernetes hit the shell, not your app, and appended arguments are ignored.

ENTRYPOINT vs CMD

ENTRYPOINT: the fixed program. CMD: default arguments, replaced by any given at run time. Together: ENTRYPOINT ["pinger"] + CMD ["https://example.com"].

.dockerignore

Keeps files out of the build context, like .gitignore. Your macOS .venv must never reach a Linux image.

.venv  dist  .git  __pycache__
.pytest_cache  .ruff_cache

3.3 Build the image and run it

Run from the folder holding the Dockerfile (uv/pinger). Docker Desktop and minikube keep separate image stores: Kubernetes only sees minikube's. Use a real tag, not latest, which makes Kubernetes pull from a registry. Either mistake gives ErrImagePull.

CommandWhat it does
Build
docker build -t pinger:0.1.0 .Build into Docker Desktop's store. -t name:tag (no tag = latest). . is the build context: the folder COPY reads from. -f FILE for another Dockerfile name.
minikube image build -t pinger:0.1.0 .Same, but built inside minikube's store, so Kubernetes can use it directly. The usual choice for the cluster.
minikube image load pinger:0.1.0Copy an image built with docker build into minikube.
Check and run
docker images pinger
minikube image ls | grep pinger		Confirm the image exists (name, tag, size) in each store.
docker run --rm pinger:0.1.0 https://example.comRun a container locally. Arguments are appended to ENTRYPOINT: runs pinger https://example.com. --rm deletes the container on exit.
kubectl run pinger-test --rm -ti \
  --image=pinger:0.1.0 --restart=Never \
  -- https://example.com		Smoke test: one bare Pod. -ti streams its output, --rm deletes it after, --restart=Never runs it once. Args after -- go to the container.

4Kubernetes: Concepts

4.1 What it's for

A container orchestrator: you declare the desired state (which images, how many copies, how to reach them) and Kubernetes keeps the cluster matching it.

SchedulingPicks a machine for each container.
Self-healingRestarts crashed containers; replaces lost Pods.
ScalingAdds or removes copies of an app.
Service discovery + load balancingA stable name; traffic spread across copies.
Rolling updates + rollbacksNew versions with no downtime; quick revert.
Declarative configDescribe it in YAML; Kubernetes keeps it so.

4.2 The physical stack (where things run)

Layer 1Process
A program on one machine, using whatever that machine has installed.
Problem: "works on my laptop" isn't guaranteed on the server.
Layer 2Image, container
A Dockerfile builds code + dependencies into an image; running it gives a container.
Problem: a lone container doesn't restart, scale, or know about other machines.
Layer 3Pod
Wraps a container (usually one) and adds an IP, labels, a restart policy and resource limits (below). A second sidecar container is added only for a helper that must share the machine, files or localhost, and live and die with the app.
Layer 4Node
A machine (physical or VM) that runs many Pods on its CPU, memory, disk and network. A container is not a machine, just a walled-off process on the node. Its agents:
  • kubelet: runs its Pods, restarts crashed containers, reports status
  • containerd: pulls images, starts and stops containers
  • kube-proxy: routes Service traffic to Pods
Layer 5Cluster, namespace
A cluster is one control plane + its worker nodes. The control plane decides (controllers: what should exist; scheduler: where), the nodes do the work. Namespaces are folders inside one cluster, spanning all its nodes (both below).
Cluster
Node
Pod
Container
Process

Pod settings: restart policy and resources

restartPolicy: when a container exits

The kubelet restarts it in the same Pod (same IP, RESTARTS +1). Repeated crashes wait longer each time (10s, 20s... 5 min): CrashLoopBackOff.

Always defaultAny exit. Required for Deployments.
OnFailureNon-zero exit only. Jobs.
NeverJobs: each retry is a new Pod.

resources: CPU and memory per container

resources:
  requests:            # reserved
    cpu: "250m"        # 1/4 of a core
    memory: "128Mi"
  limits:              # maximum
    cpu: "500m"
    memory: "256Mi"

Requests: the scheduler needs a node with that much free room, else the Pod stays Pending.

Limits: over CPU → throttled (slowed). Over memory → OOMKilled (exit 137).

Clusters: one control plane + its nodes

prod-eu                prod-us
 ├ control plane A      ├ control plane B
 └ nodes A1, A2, A3     └ nodes B1, B2
 independent: own records and decisions
  • Controllers only manage their own cluster. Companies run many (per region, environment, team).
  • kubectl talks to one at a time, its context: kubectl config current-context, use-context prod-eu. Check it before every command at work.
  • Production: control plane on dedicated nodes (often 3). minikube: one node does both.

Namespaces: folders inside one cluster

Cluster prod-eu
 ├ kube-system  etcd, apiserver, coredns
 ├ trading      Deployment pricer
 ├ risk         Deployment pricer  # OK!
 └ monitoring   prometheus, grafana
  • Separate: names (both teams can have pricer), DNS (pricer.trading.svc.cluster.local), permissions and quotas; deleting one deletes everything in it.
  • Shared: nodes. Pods from trading and risk can run on the same machine.
kubectl get namespaces                                # list them (default: "default")
kubectl get pods -n kube-system                       # one namespace
kubectl get pods -A                                   # all namespaces
kubectl create namespace dev                          # create one
kubectl config set-context --current --namespace=dev  # make dev your default

4.3 The control plane (what makes it happen)

ComponentRole
kubectlClient: sends HTTP requests to the API server.
kube-apiserverThe only front door: checks who you are, if you're allowed and if the object is valid, then saves it.
etcdKey-value store of every object (spec + status). Only the API server talks to it.
kube-schedulerWatches for Pods with no node; picks one with enough free CPU/memory; writes nodeName.
kube-controller-managerRuns the controllers: each watches one kind of object and writes records (e.g. a Pod) until status matches spec.
kubeletWatches for Pods on its node, has containerd start them, writes back status and heartbeats.
Key idea: spec vs status, and who talks to whom Every object has a spec (what you want) and a status (what's happening). The API server is passive: it validates, stores and notifies, but never gives orders. Controllers, scheduler and kubelets watch it, act when spec and status differ, and write the result back.

Example: kubectl scale deployment/bootcamp --replicas=4

1
kubectl → API server: "set replicas to 4". Checked and stored in etcd. That's all it does.
2
ReplicaSet controller notices "4 wanted, 3 exist" and writes a new Pod record.
3
Scheduler notices a Pod with no node and writes nodeName: minikube.
4
Kubelet on minikube sees a new Pod for its node, has containerd start it, writes Running.

Who fixes what: two levels of self-healing

What failedWho fixes itHow
A containerkubelet, on its ownRestarts it in the same Pod (same IP, RESTARTS +1).
A Pod or nodeControllers + schedulerNode marked NotReady (~40s), Pods evicted, ReplicaSet creates replacements on healthy nodes.

Control plane down? Running Pods keep running; you just can't change anything until it's back.

4.4 Kubernetes objects

An object is a record stored through the API server (in etcd). Pods, Deployments, Services, Jobs... all share this shape:

apiVersion: apps/v1  # API group + version
kind: Deployment     # type of object
metadata:            # name, labels
  name: kubernetes-bootcamp
spec:                # desired (you write)
  ...
status:              # actual (Kubernetes)
  ...
An object is just data It does nothing on its own. A controller (or the scheduler and kubelet, for Pods) acts on it to make reality match its spec; the table shows which.

kubectl get deployment,rs,pods shows all three layers; kubectl api-resources lists every kind.

Deploymentapps/v1Versions: rolling updates, history, rollback.DeploymentIts Pod template and replicasCreates a ReplicaSet per version; scales new up, old down

How objects connect: owners vs selectors

Deployment ──owns──▶ ReplicaSet ──owns──▶ Pods      # one ReplicaSet per version
CronJob    ──owns──▶ Job        ──owns──▶ Pods      # Jobs named pinger-cron-<minutes>
Service    ··selects by label···········▶ Pods      # routes traffic, does NOT own them
  • Owner references → garbage collection: each child records its owner (metadata.ownerReferences). Delete the owner and the garbage collector (a controller that acts on every object) deletes its children: a Deployment takes its ReplicaSets and Pods with it, a CronJob its Jobs.
  • Never create bare Pods: no controller watches a Pod, so a lost one is gone for good. Create a Deployment or Job and get all the layers for free.

5.4 Expose your app with a Service

Pods keep being replaced with new names and IPs. A Service gives them one stable name and IP, and spreads traffic across them.

CommandWhat it does

kubectl expose deployment/NAME --type=NodePort --port 8080Creates a Service that selects the Deployment's Pods by label.
kubectl describe service/NAMEShows Selector, IP, ports, and Endpoints (the live list of Pod IPs behind it).
kubectl port-forward service/NAME 9000:8080Temporary tunnel from your Mac's port 9000 to the Service's port 8080 (LOCAL:REMOTE). Only for you, until Ctrl+C.
kubectl delete service -l app=NAMEDeletes Services with this label. The Pods keep running.
kubectl run tmp --rm -ti --image=curlimages/curl --restart=Never -- curl NAME:8080Throwaway Pod to call a Service from inside the cluster, where the Service name works as a DNS hostname.
Service typeWho can reach it
ClusterIP (default)Only things inside the cluster. Service-to-service traffic.
NodePortInside the cluster + anyone who can reach a node on port 30000-32767. Dev and testing.

Every Service gets a DNS name automatically kubectl expose deployment/kubernetes-bootcamp --port 8080 creates a Service, and CoreDNS adds a name for it. Inside the cluster, both URLs reach the same Service: 
http://kubernetes-bootcamp.default.svc.cluster.local:8080   # full: any namespace
       └──── service ────┘ └─────┘ └──── suffix ───┘
                          namespace

The short name works because each Pod's DNS search list adds .default.svc.cluster.local for it. The port is the Service's --port. These names only work inside the cluster (e.g. from a Job); from your Mac, use port-forward.
The general flow 
1. kubectl create deployment  → Deployment → ReplicaSet → Pod (app on :8080, Pod IP)
2. kubectl expose deployment  → Service: stable IP + name, selects Pods by label
3. kubectl port-forward svc   → tunnel: Mac localhost:9000 → Service :8080 → Pod :8080
4. curl localhost:9000        → "Hello Kubernetes bootcamp!"

5.6 Scale your app and load balancing

CommandWhat it does
kubectl get rsShows the ReplicaSet: DESIRED, CURRENT, READY. When all three match, actual state matches desired state.
kubectl scale deployment/NAME --replicas=4Changes one number in the Deployment's spec. Controllers then create the new Pods, each with its own IP.
  • Self-healing: delete a Pod and the ReplicaSet replaces it, because actual (3) no longer matches desired (4).
  • The Service updates itself: it holds a selector rule, not a list of Pods. Any Pod with label app=kubernetes-bootcamp is added to its Endpoints automatically.
  • Load balancing: requests sent to the Service are spread across all its Pods by kube-proxy's rules on each node, per connection and at random. (port-forward bypasses this and sticks to one Pod.)

5.7 Rolling update and rollback

kubectl set image deployment/kubernetes-bootcamp  kubernetes-bootcamp=IMAGE:v2
                  └─── which Deployment ───────┘  └─ container ─────┘ └ new image

Changing the Pod template means "new version". The Deployment controller creates a second ReplicaSet for v2, then gradually moves Pods from old to new, only stopping old Pods once new ones are ready (maxSurge / maxUnavailable, both 25% by default). A broken image gets stuck while old Pods keep serving.

CommandWhat it does
kubectl rollout status deployment/NAMEWaits and reports until the rollout succeeds or fails. Used by CI/CD.
kubectl rollout history deployment/NAMELists revisions (one per template change).
kubectl rollout undo deployment/NAMEGoes back to the previous revision. --to-revision=N picks a specific one.

5.8 Declarative: apply using YAML

Every manifest has four top-level keys: apiVersion, kind, metadata, spec. Kubernetes adds status, which you never write. -f means "read the objects from this file".

CommandWhat it does
kubectl apply -f bootcamp.yamlMakes the cluster match this file (create or update). Idempotent: safe to run repeatedly.
kubectl diff -f bootcamp.yamlShows what apply would change: - lines removed, + lines added. Changes nothing.
kubectl delete -f bootcamp.yamlDeletes the objects defined in this file.
kubectl create deployment ... --dry-run=client -o yamlPrints a starting manifest instead of creating anything.

Imperative vs declarative Commands like scale and set image are for learning and emergencies. Real teams keep YAML in git and let CI/CD run apply. The next apply silently undoes any manual change.

6Kubernetes: Jobs (Batch Work)

6.1 Jobs: run to completion

A Deployment runs forever; a Job runs until it exits and is judged by the exit code: 0 → Complete; non-zero → Pod Error, retried, then Failed.

apiVersion: batch/v1
kind: Job
metadata:
  name: pinger-bad
spec:
  backoffLimit: 2              # 1 try + up to 2 retries; waits grow (10s, 20s, 40s...)
  template:
    spec:
      restartPolicy: Never     # each retry is a NEW Pod, so every attempt's logs are kept
      containers:
        - name: pinger
          image: pinger:0.1.0  # args below are APPENDED to its ENTRYPOINT
          args: ["http://kubernetes-bootcamp:8080", "http://does-not-exist:8080"]
kubectl create job NAME --image=IMG -- pinger URL   # imperative; after -- replaces ENTRYPOINT
kubectl apply -f k8s/pinger-job.yaml                # create it from YAML
kubectl get jobs                                    # STATUS, COMPLETIONS (1/1 = done)
kubectl get pods -l job-name=NAME                   # its Pods (labelled job-name=NAME)

6.2 Debugging a failed Job

1
Spot it: kubectl get jobs → pinger-bad Failed 0/1
2
What happened, and when: kubectl describe job pinger-bad
Backoff Limit:  2
Pods Statuses:  0 Active (0 Ready) / 0 Succeeded / 3 Failed
Events:
  86s  SuccessfulCreate      Created pod: pinger-bad-htvw2   # attempt 1 → exit 1
  75s  SuccessfulCreate      Created pod: pinger-bad-kw7rj   # retry 1 (~10s later)
  55s  SuccessfulCreate      Created pod: pinger-bad-lkfxg   # retry 2 (~20s later)
  52s  BackoffLimitExceeded  Job has reached the specified backoff limit
3
Why it failed: kubectl logs job/pinger-bad (one attempt) or kubectl logs -l job-name=pinger-bad (all attempts)
http://kubernetes-bootcamp:8080: 200 in 14 ms
http://does-not-exist:8080: DOWN (ConnectError: [Errno -2] Name or service not known)
4
Root cause: no Service does-not-exist → DNS fails → DOWN → exit 1 → retried → Failed. Fix the URL and re-run. Kubernetes only sees the exit code: a checker that always exits 0 would hide this.
Trap: kubectl logs job pinger-bad → pods "job" not found. logs reads its arguments as POD [CONTAINER], so this is a command typo, not the Job's failure. Use job/pinger-bad (logs and exec need the slash).

7Kubernetes Checkpoint: Questions and Answers

Cover the answers and try each question in your own words first.

1
What does "desired state and reconciliation" mean? Give an example you saw happen.

Desired state is what you declare you want (e.g. 3 replicas). Reconciliation is a loop controllers run all the time: compare actual with desired, then act to close the gap. Example: I deleted a Pod, the ReplicaSet saw 2 instead of 3, and created a new one.

2
What's the difference between a Pod, a ReplicaSet and a Deployment? Why almost never create Pods directly?

A Pod wraps containers and adds an IP, labels, restart policy and limits; it's disposable. A ReplicaSet keeps N identical Pods running. A Deployment manages ReplicaSets (one per version) for rolling updates and rollback. A bare Pod has no owner, so nothing replaces it if it dies, and it can't be scaled or rolled out.

3
Why do Services exist? What would break without them?

Pods are replaced all the time and get new IPs, and with several replicas there are several IPs. A Service gives one stable name and IP and load-balances across the current Pods. Without it, every client would have to track changing Pod IPs.

4
How does a Service know which Pods to send traffic to?

Its label selector (e.g. app=kubernetes-bootcamp). Ready Pods with matching labels appear in its Endpoints, which update automatically. Remove a Pod's label and it drops out.

5
What are the four Service types, and which is the default?

ClusterIP (default, internal only), NodePort (a port on every node), LoadBalancer (an external cloud load balancer), ExternalName (a DNS alias to an outside name).

6
During a rolling update to a broken image, why did the app keep serving traffic?

Old Pods are only removed as new ones become ready. The new Pods hit ImagePullBackOff and never became ready, so the rollout stalled with at most maxUnavailable (25%) of old Pods taken down; the rest kept serving.

7
What does kubectl rollout undo go back to?

The previous revision: the old ReplicaSet (kept at 0 replicas) is scaled back up. --to-revision=N picks a specific one from rollout history.

8
Your Pod is in CrashLoopBackOff. What are your first two commands?

kubectl describe pod NAME (Events, exit code, restart count), then kubectl logs NAME --previous (output of the run that crashed).

9
Why does the Dockerfile install dependencies before copying src/?

Layer caching: Docker re-runs every step after the first one whose inputs changed. Dependencies change rarely, code changes often, so a code edit reuses the cached dependency layer and the rebuild is fast.

10
Why does it matter that pinger exits 1 on failure when it runs as a Job?

The exit code is all Kubernetes sees. Exit 1 makes the Job retry and finally go Failed, which monitoring can alert on. If pinger always exited 0, failures would be invisible.
